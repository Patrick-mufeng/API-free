# API-free 统一面板 · 计划方案

> 2026-10-06 起草。前置决策已与用户确认：**独立聚合后端 + 全新前端**、**开关 = 真·进程启停**、**四服务面板功能全部搬进新前端（一步到位）**。
> 本文档是总计划；设计风格由 5 个 demo 原型（`prototypes/index.html`）选定后另行落地为设计规范。

---

## 1. 目标

把四个反代服务收进**一个统一前端**：

1. **统一管理**——四服务的账号、登录授权、模型、日志、设置，全部在一个界面完成，不再各自开面板；
2. **统一统计**——四服务的 token 用量数据整合展示（总览 + 按服务/模型/日期维度）；
3. **统一控制**——服务信息展示 + 真·进程启停开关（启动/停止/重启，崩溃自动拉起）。

四服务本身的代码**不改**（唯一例外见 §5 cmdgo 补丁），它们继续独立运行，面板是它们的管理层。

## 2. 总体架构

```
┌────────────────────────────────────────────────────┐
│  浏览器：统一前端 (React SPA)                       │
│  总览 · 服务×4 · 统计 · 设置                         │
└──────────────────┬─────────────────────────────────┘

┌──────────────────▼─────────────────────────────────┐
│  聚合后端 panel（Go，单进程常驻）                     │
│  ├─ 静态托管 ui/dist                                │
│  ├─ 进程监督：启停/重启/崩溃拉起/PID收编              │
│  ├─ API 代理：/api/svc/{id}/* → 各服务，注入鉴权      │
│  ├─ 统计聚合：定时拉四服务统计端点 → SQLite           │
│  └─ 面板自身 API：服务注册表、日志、配置              │
└───┬───────────┬──────────────┬──────────────┬──────┘
    │8210       │7863          │8787          │11435
┌───▼────┐ ┌────▼─────┐ ┌──────▼───┐ ┌────────▼──┐
│Qoder   │ │workbuddy │ │cline     │ │cmdgo      │
│-free   │ │-free     │ │-free     │ │-bridge    │
│(不改动) │ │(不改动)   │ │(不改动)   │ │(仅补统计)  │
└────────┘ └──────────┘ └──────────┘ └───────────┘
```

**为什么必须有聚合后端**（实测结论）：

- Qoder-free 与 workbuddy-free 无任何 CORS 头，纯前端浏览器直连会被拦截；
- 进程启停/崩溃拉起必须由常驻进程完成；
- 统计聚合需要跨服务拉数、落库、缓存。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 聚合后端 | **Go 1.25 + net/http + SQLite**（modernc.org/sqlite，免 CGO） | 与两个 Go 服务同生态；进程监督是 Go 强项；单二进制部署简单 |
| 前端 | **React 18 + Vite + TypeScript + Tailwind CSS** | 面板类应用成熟组合；图表用 **ECharts**（按需引入，支持面积图/柱图/环形） |
| 前端托管 | Vite 构建产物由 Go 后端静态托管（`panel/ui/dist`） | 一个端口一个入口，无跨域 |
| 通信 | REST + SSE（服务日志流、启停进度） | 简单够用 |

> 设计风格 demo 选定后，颜色/字体/圆角/密度等 token 以 demo 为准沉淀成 `tokens.css`。

## 5. 关键设计

### 5.1 服务注册表（`data/services.json`）

每个服务一条记录：`id、名称、目录、启动命令、端口、健康检查路径、面板 API 前缀、鉴权方式（config.json 内 api_key 字段的读取规则）、启用状态`。初始四条：

| id | 目录 | 端口 | 健康检查 | 鉴权来源 |
|---|---|---|---|---|
| qoder | Qoder-free-main | 8210 | `/v1/models`(带 key) | `config.json → api_key` |
| workbuddy | workbuddy-free-main | 7863 | `/healthz` | `config.json → api_key` |
| cline | cline-free-main | 8787 | `/v1/health` | `.env.local → API_KEY` |
| cmdgo | cmdgo-bridge-main | 11435 | `/health` | `~/.cmdgo-bridge/config.json → apiKey` |

### 5.2 进程监督（真·开关）

- **启动**：按注册表的命令在工作目录拉起子进程（Windows 下注意 Node 服务用 `node xxx` 而非脚本关联），日志重定向 `data/logs/{id}.log`；
- **停止**：杀进程树（Go `taskkill /T` 或 `JOB` 对象），防孤儿；
- **崩溃自动拉起**：退出即检测，指数退避重启（30s 起步）；
- **PID 收编**：面板重启时探测已占端口的服务进程并纳入管理，不重复拉起；
- **健康判定**：端口通 + 健康端点 200 = 运行中；仅端口通 = 启动中；否则已停止。
- 各服务启动需要的环境变量（如 cline 的 `PORT`）写在注册表里，由监督器注入。

### 5.3 API 代理（功能搬迁的通道）

`GET/POST /api/svc/{id}/*` → `http://127.0.0.1:{port}/*`，自动注入该服务的鉴权头（`Authorization: Bearer <其 api_key>`），响应原样返回，SSE 流式直通。四服务面板的所有前端调用（账号增删、登录、签到、模型、日志、配置读写）都改走这条通道，**不需要改四服务代码**。

### 5.4 统计整合

| 服务 | 数据来源 | 粒度 |
|---|---|---|
| qoder | 面板 API 每日统计 | 天 / 账号 / 模型 |
| workbuddy | 面板 API 用量统计 | 天 / 模型 / 账号 / 小时 |
| cline | `/v1/health` usage 汇总 + 面板统计 API | 天 / 模型 / 账号 |
| cmdgo | **无统计接口** → 两条路：① 给它补一个只读的 `/api/usage`（约 50 行，唯一一处服务代码改动，实施前单独征求你同意）；② 不改代码，聚合后端解析它的 `access.log`。默认走 ①，fail 时降级 ② | 需新建：天 / 模型 |

- 聚合后端每 5 分钟拉一轮 + 每次页面打开时按需刷新，写 SQLite（`panel.db`）；
- 统一 schema：`(日期, 服务, 模型, 请求数, 输入 tok, 输出 tok)`；
- 展示口径以**各服务自身统计为准**（面板只是搬运工），总览页做四服务合计与趋势。

### 5.5 前端信息架构（功能全部搬迁）

```
总览      KPI（今日 tokens/请求/活跃服务）· 30 天趋势 · 服务卡片×4（状态/今日用量/开关）· 最近请求
服务×4    每服务一个详情页，页签：
          ├─ 账号（列表/状态/额度/登录授权/删除）   ← 各服务现有面板 API
          ├─ 模型（清单/启用/冷却状态）
          ├─ 日志（请求日志/运行日志，SSE 实时）
          ├─ 任务/签到（workbuddy 签到与成长任务、qoder 国内签到）
          └─ 设置（在线编辑该服务 config）
统计      总览趋势 · 按服务/模型/日期聚合表 · 导出
设置      面板自身（服务注册表增删改、端口、开机自启说明、登录口令）
```

## 7. 风险与开放问题

1. **cmdgo 补丁**是唯一的服务代码改动（约 50 行只读统计端点），M3 动工前单独征求你同意；
2. **OAuth/设备授权回调**：四服务登录流程各异（设备码/OAuth 回调端口），统一前端发起登录没问题，但个别回调可能要求浏览器能访问服务本机端口（如 cmdgo 的 5959-5968）——本机使用场景下无碍，M2 实测；
3. **cline 端口只能用 `PORT` 环境变量改**（`.env.local` 不认端口），监督器注入即可；
4. Windows 下杀 Node 进程树要确保不误伤其他 node 进程——用 JOB 对象而不是按名杀；
5. **开放问题（不影响动工，后续确认即可）**：要不要把四服务也聚合成「一个 API 入口」（统一 base URL + 一个 key 调所有模型）？面板 v1 先不做，架构上留了位置。
